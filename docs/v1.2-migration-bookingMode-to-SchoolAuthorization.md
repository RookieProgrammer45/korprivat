# Migration plan: `bookingMode` → `SchoolAuthorization`

**Authority:** Product Spec v1.2 §1, §5, §11, §13 Phase 0–1; SC-14, SC-18.  
**Date:** 2026-10-23  
**Status:** Plan only. **Do not apply** until Phase 1 is approved after the [gap map](./v1.2-gap-map.md).

---

## Goal

Replace owner-editable `Instructor.bookingMode` (`instant` \| `request`) as the **authorization** signal with documented `SchoolAuthorization` scopes. Keep listings, financial history, and existing booking cancel / refund / support paths intact.

---

## Non-negotiable rules (§1)

1. **Legacy `bookingMode` is historical config, not authorization evidence.** Do not invent grants from `instant` or `request`.
2. After cutover, schools **without** documented authorization evidence are **directory-only**: public listing may remain searchable; booking, inquiry, and availability **entry points** must refuse (server 403 / equivalent), not silently no-op.
3. **Preserve:** existing listings, past bookings, payouts, disputes, cancel/refund/support for bookings already created.
4. **Do not** auto-activate platform default cancellation tiers as school-approved policy (SC-18). Import as draft/unverified only when Phase 2 lands.
5. Keep `Instructor.bookingMode` **readable** as legacy UI config until scopes fully replace the product surface; stop treating it as the gate for create/accept paths once scopes enforce.

## Target state (Phase 1)

| Artifact | Purpose |
| --- | --- |
| `SchoolAuthorization` | Per-listing (or school connection) grant of scopes: e.g. `directory`, `availability_display`, `inquiry_collection`, `request_to_book`, `transactional_booking`, … |
| Withdrawal / history | Append-only or versioned rows so revoked grants are auditable |
| Server checks | Booking create, accept, availability publish/read for booking, inquiry entry — deny without grant |
| Migration job | One-shot (or idempotent) job that **does not** create grants from `bookingMode` |

Exact Prisma fields ship in Phase 1; this document locks **behaviour**, not column names.

## Migration procedure (when Phase 1 runs)

### Pre-flight

1. Snapshot counts: instructors by `bookingMode`, bookings by snapshot mode, memberships without listing binding.
2. Confirm no unexpected `bookingMode` values in Neon (expect only `instant`, `request`, null).
3. Generate migration file first; never edit applied migrations; one bounded context per PR (Organizations / Verification-adjacent authz — pick one context and stick to it).

### Data steps

| Step | Action | Invents grant? |
| --- | --- | --- |
| A | Add `SchoolAuthorization` (+ history) tables empty | No |
| B | For each listing: if **no** documented evidence row exists, leave **zero** transactional / request / inquiry / availability grants | No |
| C | Optionally record a non-granting audit note that legacy `bookingMode` was `X` at cutover (config archive) | No |
| D | Do **not** map `instant` → `transactional_booking` or `request` → `request_to_book` | — |
| E | Directory listing visibility continues under existing search/activation rules until product decides otherwise | N/A |
| F | Cancellation: **no** Phase 1 policy promotion. Phase 2 may insert draft `CancellationPolicy` from `cancellationPolicyTier` with status unverified (SC-18) | No approval |

### Evidence that *would* create grants (out of band)

Only human/admin/partner flows with documented school consent create grants — not this migration. Examples (product-defined later): signed school connection, admin attestation with artefact ID, certified partner push. Phase 0 does not invent those artefacts.

### Cutover behaviour

| Surface | Without grant |
| --- | --- |
| Public directory card / profile | Still renderable (directory-only) |
| Availability calendar used for booking | Blocked |
| Inquiry / contact-to-book CTA | Blocked or replaced with non-transactional message |
| `POST /api/bookings` | 403 (scope), not 409 (mode mismatch) |
| Accept / decline / checkout on **existing** bookings | Remain available for support/lifecycle |
| Cancel / refund / dispute on existing bookings | Remain available |

## SC-14 — mandatory migration test (implement in Phase 1)

**Given:** A listing with legacy `bookingMode = 'request'` (or `instant`) and **no** `SchoolAuthorization` evidence row.  
**When:** Migration / cutover job runs.  
**Then:**

- No `request_to_book` / `transactional_booking` / `inquiry_collection` / `availability_display` grant is created.
- Public listing can still appear in directory (per existing activation).
- `POST /api/bookings` for that listing returns **403** (or documented scope denial).
- Availability booking entry points deny.
- Existing historical bookings for that listing remain readable; cancel/refund/support paths still work.

**Negative:** Assert migration logs or audit do **not** contain “inferred grant from bookingMode”.

---

## Contact / restriction survival (if data appears)

**Given:** Any listing that already behaves as contact-only or restricted (unexpected DB value, or future `contact` enum).  
**When:** Migration runs.  
**Then:** Do not upgrade to request or instant. Remain directory-only (or contact-only) until explicit grant. Prefer fail-closed.

If pre-flight finds zero `contact` rows, record that in the Phase 1 PR description and keep the test as a fixture with seeded restricted state.

---

## SC-18 — cancellation import rule (Phase 2; locked in Phase 0)

**Given:** Listing or booking snapshot uses platform tier `flexible` | `moderate` | `strict`.  
**When:** Versioned `CancellationPolicy` lands.  
**Then:**

- Import creates **draft / unverified** policy rows only.
- Must **not** set school-approved / active without school action.
- Bookings already snapshotting a tier continue to use the **snapshot** for cancel math until policy versioning is wired.

Phase 1 must not “fix” this by treating code defaults as approved school policy.

---

## SC-19 note (adjacent, not invented grants)

Org affiliation today is Membership-by-user, not verified listing↔org binding. Directory-only cutover must not assume `Booking.organizationId` proves listing ownership. Binding work is separate; migration must not invent `ListingOrgBinding` from Membership alone without product rules.

---

## Rollback posture

- Prefer feature-flag: enforce scope checks behind flag; leave `bookingMode` gates until flag on.
- Do not delete `bookingMode` columns in Phase 1.
- If Phase 1 must revert: turn off scope enforcement; listings return to mode-based 409 behaviour; empty `SchoolAuthorization` tables are harmless.
