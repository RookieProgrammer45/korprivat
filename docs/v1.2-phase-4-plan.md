# Phase 4 plan — Connectivity API

**Authority:** specs/09 §7 and §13 Phase 4. Acceptance: SC-7 and SC-9.  
**Status:** in review at https://github.com/RookieProgrammer45/korprivat/pull/32. Not merged.  
**Flag:** `CONNECTIVITY_API` defaults off. While off, `/v1` routes and production enablement respond 404.

## What this phase does

- Partner requests carry `X-DLU-Partner-Id`, `X-DLU-Timestamp` (±5 minutes), `X-DLU-Signature` (HMAC-SHA256 over method + path + timestamp + body), and `X-DLU-Connection-Id`.
- A credential is bound to one connection and one environment. Using it against another connection is 403. Sandbox credentials cannot act on production connections.
- Idempotency keys are unique per connection and operation type. The same key with a different payload is `422 idempotency_key_conflict`.
- Availability upserts are stored as idempotent operations. They do not create public bookable slots. Content is stored as a draft with `published: false`.
- Inbound events use the Phase 3 inbox. A request rejected with 429 is not stored.
- Adapter request and response schemas match §7.2. The mock hold returns a full hold or a conflict, never a partial reservation.
- Production enablement from mock evidence is refused. Vendor-environment evidence is recorded and still does not turn booking on. Milestone 5 remains a later phase.

Secrets stay in `CONNECTIVITY_PARTNER_SECRETS`, not in the database and not in source.

## Out of this phase

Partner registry screens, capability-scoped `prod_enabled` for live booking, and any call to a vendor host.
