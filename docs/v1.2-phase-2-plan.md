## What ships

Bounded context: **Scheduling** (`src/lib/scheduling/`). One additive Prisma migration. Empty tables are safe for `prisma db push`.

### Policy service

`src/lib/scheduling/booking-policy.ts` — one function per action. Returns the first failing component (`E0`–`E4`) or ok. The UI does not reimplement it.

| Action | Checks |
| --- | --- |
| Request submission | E0–E3. No E4. No hold. |
| Instant create | E0–E4. E4 passes only for the native slot route (the slot lock that already exists). |
| Manual accept | E0–E3 again. E4 not required. Persist `commitmentRoute`: `native` or `external_manual`. No connector required (SC-16). |
| Confirm / reschedule | E0–E4 on the instant path. |

Unknown eligibility blocks the action. Missing E4 on instant create does not delete `request_to_book` when that scope is granted.

### State machine

`BookingStateTransition`: `id`, `bookingId`, `fromState`, `toState`, `actor`, `correlationId`, `createdAt`. Append-only.

Allowed canonical edges are the §6.2 table. `cancelled → no_show` is rejected. `expired` is terminal.

Mapper from live `paymentStatus` (read-only): `awaiting_approval` → `pending`, `held_escrow` / `awaiting_buyer_confirmation` / `release_ready` → `confirmed` or `in_progress` as recorded on the transition, `released` → `completed`, cancel/refund statuses → `cancelled`. The mapper does not write `paymentStatus`.

### Payments and concurrency

- SC-15: if a capture arrives for a booking already `expired`, leave it `expired`, set `PaymentRecord.lateCaptured`, and create an `OpsTask` whose only actions are void/refund or a new booking. Do not confirm.
- SC-6: two concurrent instant creates for one slot — one succeeds, the other 409, and the loser does not leave `bookedAt` set. Test the existing `updateMany` in [`src/app/api/bookings/route.ts`](../src/app/api/bookings/route.ts). No new Hold table.
- `PaymentRecord` is additive and written only from the Stripe webhook path. It does not replace columns on `Booking`.

### Cancellation policy

`CancellationPolicy`: listing id, version, deadline type, deadline value, timezone, business calendar, wording, source, `approvedAt`, state `draft | active | withdrawn`. At most one `active` row per listing (same active-key pattern as `ListingOrgBinding`).

Import job: each legacy `flexible` / `moderate` / `strict` becomes a **draft** row. It does not set `approvedAt`. It does not rewrite `Booking.cancellationPolicyTier`.

Deadline helper: “13:00 previous business day” on a Mon–Fri calendar, Monday 10:00 lesson → Friday 13:00 school-local (SC-10). Snapshot that deadline onto the booking only when enforcement is on and an active policy exists. When enforcement is on and no active policy exists, the public profile omits policy text and new checkout returns 403. When enforcement is off, current tier copy and checkout stay.

School approval is an explicit action by a verified representative (Phase 1 authority). A draft does not become active by import.
