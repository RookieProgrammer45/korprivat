# Phase 3 plan — Reliable processing

**Authority:** specs/09 §6.4 and §13 Phase 3, plus SC-20 from §15. Workflow also requires the outbox insert to share the booking transaction.  
**Status:** in progress on `feat/phase-3-reliable-processing`.  
**Flag:** `RELIABLE_PROCESSING` defaults off. While off, booking create does not write an outbox row and the inbox route responds 404.

## What this phase does

- Durable `BookingEvent` inbox. A duplicate provider event returns 202 `rejected_duplicate` and does not move the watermark. An older revision or occurrence time is `rejected_stale`. Equal or missing order stays unapplied and asks for authoritative retrieval. Nothing is guessed.
- Durable `CommandOutbox`. A native booking state change writes the outbox row in the same transaction as the booking insert, and only when the flag is on.
- Bounded retries (5 attempts, 30s initial, 1h cap). Exhaustion dead-letters a redacted payload and opens an ops task. The event is not deleted.
- Quarantine on an unresolved remote command stays until an authoritative result or an audited decision with a rationale. TTL expiry and retry exhaustion do not release it.
- `SchoolConnection` exists only as the inbox tenant. It starts `inactive`. No partner credentials, no HMAC, no vendor calls. Signing is Phase 4.

## Conflict recorded

specs/09 updates inbox and outbox rows as they are processed. The repo rule that names `VerificationEvent`, `AdminAction`, and `StripeWebhookEvent` as append-only does not fit a status that must change. specs/09 wins. These rows are never deleted.

## Out of this phase

Partner HTTP, webhook signing, sandbox credentials, certification, and commission changes.
